# 热附着与热重载

这两个特性解决的是同一件事：**改代码不该付出「退出 QQ、重新登录」的代价**。一次完整重启是 40 秒左右，外加一次扫码/滑块登录；这两条把常见改动压到 0~14 秒。

## 热附着：重启 OpenQQ 不重启 QQ

### 它凭什么能成立

QQ 侧的原生脚本（`native/session.cjs`）注入后不会因为 OpenQQ 退出而卸载，它只是断开了 IPC 连接，然后每 300 毫秒重连同一个端点。所以只要端点地址和令牌是固定的，OpenQQ 重新起来就能「接回」原来那个 QQ 进程。

端点名与令牌持久化在 `.runtime/ipc.json`：

```json
{ "pipe": "\\\\.\\pipe\\openqq-<32 位随机十六进制>", "token": "<64 位随机十六进制>" }
```

- 端点名是**随机的**，不由项目路径推导。可推导的名字意味着本机任何进程都能提前算出并占住它，从而拿到 QQ 侧 `hello` 帧里的令牌、进而下发动作帧。
- 删掉这个文件等于「忘记端点」：下次启动会生成新端点，此时必须重启 QQ 才能重新注入。

### 启动时怎么判断

```
QQ 没在运行            → 照常拉起原生启动器，由它启动 QQ 并注入
QQ 在运行 + 6 秒内连回来 → 直接附着，完全不碰 QQ（约 14 秒就绪）
QQ 在运行 + 没连回来     → 报错「请先手动退出 QQ」，然后退出
```

第三种情况就是「那个 QQ 不是我们注入的实例」（比如你自己日常用的号）。这时既不能附着，也不能再拉一个启动器往一个已经跑着的 QQ 里重复注入，所以只能请你先退出 QQ。

> 如果你同时开了两个 QQ 账号：附着只针对**注入了原生脚本的那个进程**，另一个不受影响。但两者如果是在同一个客户端里切号，就无法区分。

### 断开时会发生什么

- OpenQQ 退出：QQ 侧继续重连，包装保持原位，QQ 照常用。
- QQ 退出：OpenQQ 收到 `disconnected` 后按原逻辑收尾。

## 热重载：改 `native/actions.cjs` 不重启任何进程

`native/session.cjs` 在运行时 `require` 同目录的 `actions.cjs`，每次执行动作前比对文件 mtime，变了就清掉同目录下所有已载入的 `.cjs` 缓存再重新 `require`，然后换上新 handler。

清整个目录而不是写死一张依赖清单，是因为「清单漏了新模块」的表现极具误导性：`actions.cjs` 明明重载了，它 require 的兄弟模块还是旧的，于是「表里加了动作却回 尚未支持动作」。

### 边界（实测）

| 改动 | 热重载是否生效 |
| --- | --- |
| handler 里的逻辑（返回值、参数构造、内部流程） | 有效 |
| `validateAction` 里**已有分支**的返回值 | 有效 |
| `validateAction` 里**新增**一个 `if (request.action === '…')` 分支 | 无效，需要重启 |
| 给动作表**新增键**（如 OIDB 动作表） | 无效，需要重启 |
| `native/session.cjs` 本身 / `native/*.cpp` | 必须重启 QQ |

原因：`validateAction` 与 handler 各自持有一份引用，重载只换掉了后者。所以「只改逻辑就直接改」，只要动到动作的**注册面**就顺手重启一次。

### 怎么确认重载生效了

重载成功会往 QQ 侧的标准错误写一行：

```
[hot] reloaded actions.cjs mtime=<毫秒时间戳>
```

这行会落到 `.runtime/qq.log`。重载失败不会静默：

```
[hot] reload failed: <堆栈>
```

失败时保留旧 handler，动作继续按旧逻辑执行。

## 事件丢弃

OpenQQ 不在时事件没有去处。`native/session.cjs` 不静默 `return`，而是计数并每分钟最多写一条：

```
[ipc] event dropped (no connection); dropped so far=12
```

`dropped so far` 是本次注入以来的累计值。重启 OpenQQ 期间丢了多少条消息，看这行就能判断。
